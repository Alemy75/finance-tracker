# Технический проект

Этот документ развивает [проект первой версии](PRODUCT_SPEC.md). Интерфейс согласован для двух iPhone и браузера на компьютере. Облачная инфраструктура целиком размещается на Cloudflare.

## Компоненты

```text
React + Vite PWA на iPhone / в браузере
  ├─ service worker: запуск ранее открытого приложения без сети
  ├─ IndexedDB: локальные записи и очередь изменений
  └─ HTTPS API → Cloudflare Worker → Cloudflare D1
                    └─ Better Auth: общий email и пароль
```

Cloudflare Worker отдаёт файлы приложения через Static Assets и обрабатывает API. D1 хранит общие данные. Better Auth использует D1 для учётной записи и сессий. Первый вход на новом устройстве выполняется при наличии сети; после него приложение может работать с локальной копией данных без сети.

Каркас использует Cloudflare Vite plugin для сборки Worker и Static Assets, а `vite-plugin-pwa` создаёт манифест и service worker. Локальная разработка запускается через `pnpm dev`.

Общий профиль и сессии работают через Better Auth и D1. Первое создание профиля требует отдельного ключа настройки; уникальный индекс в D1 не позволяет создать второй профиль даже при одновременных запросах. После входа Worker создаёт начальные категории в D1. Стартовый капитал, категории интерфейса, операции, цели и движения средств целей сохраняются в IndexedDB и синхронизируются с D1. Каждая локальная запись атомарно сохраняется вместе с командой в очереди. При обновлении старой локальной базы уже введённые данные ставятся в эту очередь и переносятся в общий профиль. Удаление операции сохраняет отметку, которую получает второе устройство. Клиент и сервер проверяют доступную свободную сумму при выделении денег и остаток цели при возврате или расходе из неё. Интерфейс показывает число ожидающих команд и конфликты. Ранее вошедшее устройство открывает локальные записи без сети, используя локальную отметку о последнем подтверждённом входе.

## Правила данных

- Единственная валюта — RUB. Все суммы хранятся целыми копейками.
- Один общий пользователь соответствует одному семейному набору данных. Автор операции (`я`, `жена`, не указан) — необязательная пометка, не отдельная учётная запись.
- Начальный капитал задаётся при первой настройке и считается начальным остатком карты.
- В записи отдельно хранятся дата и время операции, заданные пользователем, и момент создания записи. Отчёт за месяц использует дату операции.
- Остаток карты вычисляется из начального капитала, доходов и расходов. Пополнения целей не входят в расходы.
- Деньги, выделенные на цель, вычисляются из движений цели за вычетом расходов, оплаченных из неё.
- Свободная сумма = остаток карты − сумма, выделенная на все цели. На главном экране это главный показатель.
- Отрицательный остаток карты или свободная сумма отображаются явно: расход отражает фактическую запись, даже если ранее не был внесён доход или не была освобождена сумма из цели.

## Основные таблицы D1

| Таблица | Содержимое |
| --- | --- |
| `settings` | ID общего пользователя, начальный капитал, дата начала учёта, часовой пояс отображения |
| `categories` | Тип (доход/расход), название, порядок, признак архивации |
| `transactions` | Сумма, тип, категория, дата и время операции, автор, заметка, необязательная цель для расхода, версия и признак удаления |
| `goals` | Название, желаемая сумма, версия и признак архивации |
| `goal_moves` | Выделение денег на цель или возврат в свободную сумму; сумма со знаком, дата, уникальный ID |
| `mutations` | Уникальный ID принятого изменения, устройство, результат применения; нужен для защиты от дублей |
| `change_log` | Монотонный номер изменения и обновлённая сущность; обеспечивает сериализацию финансовых команд и журнал изменений |

Таблицы Better Auth для учётной записи и сессий создаются миграцией `migrations/0002_better_auth.sql`. Каждая таблица приложения содержит ID общего пользователя; Worker берёт его из проверенной сессии, а не из присланного клиентом значения. Удаление операций и целей выполняется пометкой, чтобы второе устройство тоже получило удаление.

Первая миграция — `migrations/0001_initial.sql`. ID категории, операции и цели уникален внутри общего пользователя; составные внешние ключи не дают привязать запись к категории или цели другого пользователя. Денежные поля — целые копейки, для операций и целей действуют ограничения положительности. `change_log.seq` возрастает глобально. Начальные категории создаются идемпотентно при первом подтверждённом запросе статуса общего профиля.

## API

- `GET /api/bootstrap` — полная актуальная копия данных и номер последнего изменения для устройства.
- `POST /api/sync` — одна локальная команда с уникальным ID; возвращает подтверждение или конфликт с общей версией.
- `GET /api/export` — доступная только после входа выгрузка пользовательских строк D1 в JSON. Выгружаются настройки, категории, цели, движения целей, операции и метаданные синхронизации; данные авторизации не включаются.
- Маршруты Better Auth — создание общего профиля, вход, выход и работа с сессией.
- `GET /api/account/status` — наличие профиля и текущая подтверждённая сессия; при первом входе создаёт начальные категории.

API проверяет типы данных, положительность суммы операции, существование категории и принадлежность каждой записи текущему пользователю. Одна и та же локальная команда может безопасно отправляться повторно: сервер узнаёт её по ID и возвращает прежний результат.

Для Better Auth включена совместимость Worker с Node API. Создание профиля и вход успешно проверены на отдельном размещённом Worker; ошибка лимита CPU не возникла. Точное время CPU этой проверкой не измерялось. Семейная база остаётся без профиля до первого входа владельца.

## Синхронизация

1. При сохранении операция сразу попадает в IndexedDB и видна в интерфейсе. Очередь показывает число изменений, ожидающих отправки.
2. При открытии приложения и возвращении сети клиент получает актуальную копию, отправляет очередь по порядку и получает обновлённую копию. Полные копии выбраны для небольшого семейного набора данных; журнал изменений сохраняется для контроля порядка и будущей оптимизации.
3. Новые независимые операции объединяются. Для редактирования и удаления клиент отправляет версию записи, на которой основано изменение.
4. Если запись уже была изменена на другом устройстве, сервер сохраняет текущую версию и возвращает конфликт. Локальная правка остаётся на устройстве до выбора пользователем версии.
5. Выделение денег на цель и расход из цели проверяются на сервере по актуальным суммам. Если две офлайн-записи претендуют на одни и те же выделенные деньги, более поздняя при синхронизации требует исправления и не теряется из очереди.
6. Изменение записи, движение цели, журнал изменений и отметка принятой команды записываются атомарно через D1 `batch()`. Команда проверяет номер последнего изменения внутри того же пакета: два одновременных выделения не могут использовать одну и ту же свободную сумму. Независимая команда автоматически повторяется после изменения общего номера.

Обычный расход не блокируется из-за недостаточного расчётного остатка: приложение показывает отрицательную свободную сумму и позволяет исправить пропущенные операции или вернуть деньги из цели. Выход из профиля не удаляет локальные данные и очередь; они остаются на устройстве до следующего входа.

## Резервное восстановление

- В настройках доступна выгрузка полного набора финансовых данных и метаданных синхронизации в JSON для долгосрочного хранения пользователем. Клиент перед ней отправляет локальную очередь и не скачивает файл, пока остаются неотправленные изменения или конфликты. Сервер считывает таблицы одной транзакцией D1 `batch()`; файл не содержит паролей и сессий.
- D1 Time Travel позволяет откатить базу за последние 7 дней на Workers Free и за 30 дней на Workers Paid. Откат всей базы — административная операция; перед ним делается свежая выгрузка.
- Time Travel работает только с удалённой D1. Пробный откат и возврат к прежнему состоянию проверены на отдельной удалённой тестовой базе `family-finance-tracker-staging` до использования семейной базы.
- Восстановление пользовательского JSON предусматривается как административная процедура с проверкой схемы и дубликатов. Автоматический импорт через интерфейс не входит в первую версию.

## Порядок реализации

1. Каркас PWA, локальные данные, первый экран и форма быстрого ввода.
2. D1 схема, Better Auth и защищённый API.
3. История, категории, цели и расчёты.
4. Очередь офлайн-изменений, синхронизация двух устройств и конфликты.
5. Экспорт, проверка на двух iPhone и развёртывание Cloudflare.
