# Технический проект

Этот документ развивает [проект первой версии](PRODUCT_SPEC.md). Интерфейс согласован для двух iPhone и браузера на компьютере. Облачная инфраструктура целиком размещается на Cloudflare.

## Компоненты

```text
React + Vite PWA на iPhone / в браузере
  ├─ service worker: запуск ранее открытого приложения без сети
  ├─ IndexedDB: локальные записи и очередь изменений
  └─ HTTPS API → Cloudflare Worker → Cloudflare D1
                    └─ Better Auth: общий email и пароль
```

Cloudflare Worker отдаёт файлы приложения через Static Assets и обрабатывает API. D1 хранит общие данные. Better Auth использует D1 для учётной записи и сессий. Первый вход на новом устройстве выполняется при наличии сети; после него приложение может работать с локальной копией данных без сети.

Каркас использует Cloudflare Vite plugin для сборки Worker и Static Assets, а `vite-plugin-pwa` создаёт манифест и service worker. Локальная разработка запускается через `pnpm dev`.

На текущем этапе стартовый капитал, начальные категории и операции уже сохраняются в IndexedDB одного браузера. Очередь изменений, общий вход и синхронизация с D1 появятся в следующих этапах; интерфейс явно показывает, что данные пока остаются только на устройстве.

## Правила данных

- Единственная валюта — RUB. Все суммы хранятся целыми копейками.
- Один общий пользователь соответствует одному семейному набору данных. Автор операции (`я`, `жена`, не указан) — необязательная пометка, не отдельная учётная запись.
- Начальный капитал задаётся при первой настройке и считается начальным остатком карты.
- В записи отдельно хранятся дата и время операции, заданные пользователем, и момент создания записи. Отчёт за месяц использует дату операции.
- Остаток карты вычисляется из начального капитала, доходов и расходов. Пополнения целей не входят в расходы.
- Деньги, выделенные на цель, вычисляются из движений цели за вычетом расходов, оплаченных из неё.
- Свободная сумма = остаток карты − сумма, выделенная на все цели. На главном экране это главный показатель.
- Отрицательный остаток карты или свободная сумма отображаются явно: расход отражает фактическую запись, даже если ранее не был внесён доход или не была освобождена сумма из цели.

## Основные таблицы D1

| Таблица | Содержимое |
| --- | --- |
| `settings` | ID общего пользователя, начальный капитал, дата начала учёта, часовой пояс отображения |
| `categories` | Тип (доход/расход), название, порядок, признак архивации |
| `transactions` | Сумма, тип, категория, дата и время операции, автор, заметка, необязательная цель для расхода, версия и признак удаления |
| `goals` | Название, желаемая сумма, версия и признак архивации |
| `goal_moves` | Выделение денег на цель или возврат в свободную сумму; сумма со знаком, дата, уникальный ID |
| `mutations` | Уникальный ID принятого изменения, устройство, результат применения; нужен для защиты от дублей |
| `change_log` | Монотонный номер изменения и обновлённая сущность для синхронизации устройств |

Таблицы Better Auth для учётной записи и сессий создаются отдельно. Каждая таблица приложения содержит ID общего пользователя; Worker берёт его из проверенной сессии, а не из присланного клиентом значения. Удаление операций и целей выполняется пометкой, чтобы второе устройство тоже получило удаление.

## API

- `GET /api/bootstrap` — полная актуальная копия данных и номер последнего изменения для нового устройства.
- `POST /api/sync` — отправка локальных изменений с уникальными ID и получение изменений после последнего известного номера.
- `GET /api/export` — резервная копия данных пользователя в JSON.
- Маршруты Better Auth — создание общего профиля, вход, выход и работа с сессией.

API проверяет типы данных, положительность суммы операции, существование категории и принадлежность каждой записи текущему пользователю. Одна и та же локальная команда может безопасно отправляться повторно: сервер узнаёт её по ID и возвращает прежний результат.

## Синхронизация

1. При сохранении операция сразу попадает в IndexedDB и видна в интерфейсе. Очередь показывает число изменений, ожидающих отправки.
2. При открытии приложения и возвращении сети клиент отправляет очередь по порядку и запрашивает изменения второго устройства.
3. Новые независимые операции объединяются. Для редактирования и удаления клиент отправляет версию записи, на которой основано изменение.
4. Если запись уже была изменена на другом устройстве, сервер сохраняет текущую версию и возвращает конфликт. Локальная правка остаётся на устройстве до выбора пользователем версии.
5. Выделение денег на цель и расход из цели проверяются на сервере по актуальным суммам. Если две офлайн-записи претендуют на одни и те же выделенные деньги, более поздняя при синхронизации требует исправления и не теряется из очереди.
6. Изменение записи, движение цели, журнал изменений и отметка принятой команды записываются атомарно. D1 поддерживает атомарный `batch()`; конкретные команды и ограничения проверяются интеграционными тестами.

Обычный расход не блокируется из-за недостаточного расчётного остатка: приложение показывает отрицательную свободную сумму и позволяет исправить пропущенные операции или вернуть деньги из цели. Если устройство выходит из профиля с неотправленными изменениями, приложение предупреждает до удаления локальных данных.

## Резервное восстановление

- В настройках доступна выгрузка полного набора данных в JSON для долгосрочного хранения пользователем.
- D1 Time Travel позволяет откатить базу за последние 7 дней на Workers Free и за 30 дней на Workers Paid. Откат всей базы — административная операция; перед ним делается свежая выгрузка.
- Восстановление пользовательского JSON предусматривается как административная процедура с проверкой схемы и дубликатов. Автоматический импорт через интерфейс не входит в первую версию.

## Порядок реализации

1. Каркас PWA, локальные данные, первый экран и форма быстрого ввода.
2. D1 схема, Better Auth и защищённый API.
3. История, категории, цели и расчёты.
4. Очередь офлайн-изменений, синхронизация двух устройств и конфликты.
5. Экспорт, проверка на двух iPhone и развёртывание Cloudflare.
